## 1. Plugin Lifecycle

### Purpose

ZenithProxy plugins are external JARs loaded at startup. ZenithProxy discovers them, validates compatibility, instantiates them, and calls `onLoad()`. There is **no hot-reload** -- plugins are loaded once, at proxy boot.

### Important Classes

| Class | Package | Role |
|---|---|---|
| `ZenithProxyPlugin` | `com.zenith.plugin.api` | Interface all plugins must implement |
| `@Plugin` | `com.zenith.plugin.api` | Annotation carrying metadata (id, version, mcVersions, authors, etc.) |
| `PluginAPI` | `com.zenith.plugin.api` | Interface passed to `onLoad()`; the plugin's gateway to Zenith |
| `PluginInfo` | `com.zenith.plugin.api` | Immutable record of the `@Plugin` annotation data |
| `PluginManager` | `com.zenith.plugin` | Internal class that scans `plugins/` folder, opens `URLClassLoader`s, parses `zenithproxy.plugin.json`, and calls `onLoad()` |

### How It Works

1. **Discovery**: `PluginManager` scans the `plugins/` directory for `.jar` files.
2. **Metadata**: Each JAR must contain `zenithproxy.plugin.json` at the root, which is generated by the `zenithproxy.plugin.dev` Gradle plugin from the `@Plugin` annotation.
3. **Compatibility check**: `mcVersions` in `PluginInfo` is compared against the running ZenithProxy MC version. A `"*"` wildcard means "any version".
4. **Class loading**: A `URLClassLoader` is opened for the JAR, with the ZenithProxy system classloader as parent.
5. **Instantiation**: The entrypoint class is loaded and instantiated (no-arg constructor). It must implement `ZenithProxyPlugin`.
6. **Load**: `onLoad(PluginAPI)` is called. This is where the plugin registers configs, modules, and commands.

### Example Usage

```java
@Plugin(
    id = "my-plugin",
    version = "1.0.0",
    description = "My Plugin",
    url = "https://github.com/me/my-plugin",
    authors = {"me"},
    mcVersions = {"1.21.4"}
)
public class MyPlugin implements ZenithProxyPlugin {
    public static MyConfig CONFIG;
    public static ComponentLogger LOG;

    @Override
    public void onLoad(PluginAPI pluginAPI) {
        LOG = pluginAPI.getLogger();
        LOG.info("Loading...");
        CONFIG = pluginAPI.registerConfig("my-config", MyConfig.class);
        pluginAPI.registerModule(new MyModule());
        pluginAPI.registerCommand(new MyCommand());
        LOG.info("Loaded.");
    }
}
```

### How a Plugin Interacts

- A plugin **must** be a class implementing `ZenithProxyPlugin` annotated with `@Plugin`.
- `onLoad(PluginAPI)` is the sole entry point. Register configs first (they must exist before modules read them), then modules, then commands.
- `PluginAPI.getLogger()` returns a `ComponentLogger` pre-configured for the plugin.
- `PluginAPI.registerConfig(fileName, Class)` auto-serializes a POJO to/from JSON at `plugins/config/<fileName>.json`. Config is auto-saved on proxy shutdown and every command execution.

## 2. Dependency Injection (Globals)

### Purpose

ZenithProxy does **not** use a DI framework. All services are **static singletons** exposed via `com.zenith.Globals`. Plugins import them statically.

### Important Classes

| Field | Type | Purpose |
|---|---|---|
| `Globals.EVENT_BUS` | `SimpleEventBus` | Publish/subscribe event system |
| `Globals.MODULE` | `ModuleManager` | Registry of all modules (built-in + plugin) |
| `Globals.CACHE` | `DataCache` | All cached world state (chunks, entities, inventory, player, etc.) |
| `Globals.BARITONE` | `Baritone` | Pathfinder / bot control |
| `Globals.INVENTORY` | `InventoryManager` | Queued inventory actions |
| `Globals.INPUTS` | `InputManager` | Queued movement/look input |
| `Globals.COMMAND` | `CommandManager` | Command dispatcher |
| `Globals.BOT` | `Bot` | Low-level bot simulation |
| `Globals.DISCORD` | `DiscordBot` | Discord integration |
| `Globals.CONFIG` | `Config` | Main ZenithProxy configuration |
| `Globals.EXECUTOR` | `ScheduledExecutorService` | Shared scheduler |
| `Globals.BLOCK_DATA` | `BlockDataManager` | Block ID ↔ properties registry |
| `Globals.ENTITY_DATA` | `EntityDataManager` | Entity type registry |
| `Globals.PLAYER_LISTS` | `PlayerListsManager` | Player list/whitelist management |
| `Globals.TPS` | `TPSCalculator` | Server TPS tracking |

Additionally, `com.zenith.Proxy` is a singleton accessed via `Proxy.getInstance()`.

### Example Usage

```java
import static com.zenith.Globals.*;

// Access the module registry to find a module
ExampleWanderModule wander = MODULE.get(ExampleWanderModule.class);

// Access the player cache
double x = CACHE.getPlayerCache().getX();
double y = CACHE.getPlayerCache().getY();
double z = CACHE.getPlayerCache().getZ();

// Access the pathfinder
BARITONE.pathTo(1000, 0, 1000);

// Get active player connections
ServerSession[] sessions = Proxy.getInstance().getActiveConnections().getArray();
```

### How a Plugin Interacts

- Use `import static com.zenith.Globals.*` to access all singletons.
- `Proxy.getInstance()` gives access to client connections, active sessions, and the controlling player.
- There is no constructor injection. Everything is accessed statically.

## 3. Command Registration

### Purpose

ZenithProxy commands work across three surfaces: **terminal**, **in-game chat**, and **Discord**. They are built with Mojang Brigadier and registered via `PluginAPI.registerCommand()`.

### Important Classes

| Class | Role |
|---|---|
| `Command` (abstract) | Base class plugins extend. Provides `command()`, `literal()`, `argument()`, `toggle()`, embed helpers, and error handling. |
| `CommandUsage` | Immutable builder pattern for declaring the command name, category, description, and usage lines. |
| `CommandContext` | Execution context: carries `input`, `source` (term/player/spectator/discord), in-game player info, and an `Embed` builder. |
| `CommandCategory` | Enum: `CORE`, `INFO`, `MANAGE`, `MODULE`. |
| `Embed` | Builder for Discord-style embed responses (title, description, fields, color). |
| `CommandSource` | Interface for the origin of the command. |
| `ToggleArgumentType` | Custom Brigadier argument for `on`/`off` boolean parsing. |
| `LiteralArgumentBuilder` | Brigadier builder for literal nodes. |
| `ZRequiredArgumentBuilder` | Brigadier builder for required argument nodes. |

### How It Works

1. Extend `Command`.
2. Override `commandUsage()` to return metadata.
3. Override `register()` to return a Brigadier tree using `command("name").then(...).executes(...)`.
4. Optionally override `defaultEmbed(Embed)` to show current state when the command is invoked without args.
5. Register via `pluginAPI.registerCommand(new MyCommand())`.

The `command("name")` factory automatically attaches default success/error handlers that populate the embed. Return `Command.OK` or `Command.ERROR` from execution lambdas.

The `Embed` builder is mutable and carries through the command pipeline. If `title` is set, an embed response is sent to the source. If no title is set, no response is sent.

### Example Usage

```java
public class MyCommand extends Command {
    @Override
    public CommandUsage commandUsage() {
        return CommandUsage.builder()
            .name("mycommand")
            .category(CommandCategory.MODULE)
            .description("My custom command")
            .usageLines("on/off", "value <int>")
            .build();
    }

    @Override
    public LiteralArgumentBuilder<CommandContext> register() {
        return command("mycommand")
            .then(argument("toggle", toggle()).executes(c -> {
                boolean val = getToggle(c, "toggle");
                c.getSource().getEmbed().title("MyCommand " + toggleStrCaps(val));
            }))
            .then(literal("value").then(argument("int", integer(1, 100)).executes(c -> {
                int val = getInteger(c, "int");
                c.getSource().getEmbed().title("Value set to " + val);
            })));
    }
}
```

### How a Plugin Interacts

- Extend `Command`, implement `commandUsage()` and `register()`.
- Call `pluginAPI.registerCommand(...)` in `onLoad()`.
- Use `c.getSource().getEmbed()` to return formatted output.
- Access config via a static reference to the plugin's config object.
- Use `MODULE.get(ModuleClass.class).syncEnabledFromConfig()` to sync toggled state.

## 4. Module System

### Purpose

Modules are the primary unit of bot behavior. Each module can be toggled on/off (via config), subscribe to events, and register packet handlers. They have a well-defined `enable`/`disable` lifecycle.

### Important Classes

| Class | Role |
|---|---|
| `Module` (abstract) | Base class. Manages `enabled` state, event subscription, and packet handler codec registration. |
| `ModuleUtils` (abstract) | Superclass providing logging helpers (`debug`, `info`, `warn`, `error`), packet send helpers (`sendClientPacket`, `sendClientPacketAsync`, `sendClientPacketAwait`), in-game alert methods, and Discord notification methods. |
| `ModuleManager` | Registry of all modules. `get(Class)` returns a module instance. |

### How It Works

**Lifecycle:**

```
  new Module()
  ↓
  onLoad → syncEnabledFromConfig()  (reads enabledSetting())
  ↓
  if true → enable()
              → subscribeEvents()     (EVENT_BUS.subscribe(this, ...))
              → register*PacketHandlerCodec()  (registers with PacketCodecRegistries)
              → onEnable() hook
  ↓
  disable()
              → unsubscribeEvents()   (EVENT_BUS.unsubscribe(this))
              → unregister packet codecs
              → onDisable() hook
```

**Key overridable methods on Module:**

| Method | Purpose |
|---|---|
| `enabledSetting()` | **Required.** Returns `true/false` based on config. Determines if the module auto-enables on startup. |
| `registerEvents()` | Return a `List<EventConsumer<?>>` of event listeners. |
| `registerClientPacketHandlerCodec()` | Register handlers for packets between Zenith and the destination Minecraft server. |
| `registerServerPacketHandlerCodec()` | Register handlers for packets between Zenith and connected players (controlling player + spectators). |
| `onEnable()` | Hook called when module becomes enabled. |
| `onDisable()` | Hook called when module becomes disabled. |
| `syncEnabledFromConfig()` | Re-reads `enabledSetting()` and enables/disables accordingly. |

### Example Usage

```java
public class MyModule extends Module {
    final Timer timer = Timers.tickTimer();

    @Override
    public boolean enabledSetting() {
        return MyPlugin.CONFIG.myModule.enabled;
    }

    @Override
    public List<EventConsumer<?>> registerEvents() {
        return List.of(
            of(ClientBotTick.class, this::handleBotTick)
        );
    }

    private void handleBotTick(ClientBotTick event) {
        if (timer.tick(100L)) {
            info("Tick!");
        }
    }

    @Override
    public void onDisable() {
        BARITONE.stop();
    }
}
```

**Packet handler example:**

```java
@Override
public PacketHandlerCodec registerServerPacketHandlerCodec() {
    return PacketHandlerCodec.serverBuilder()
        .setId("my-handler")
        .setPriority(1000)
        .state(ProtocolState.GAME, PacketHandlerStateCodec.serverBuilder()
            .inbound(ClientboundSetEntityDataPacket.class, new PacketHandler<>() {
                @Override
                public ClientboundSetEntityDataPacket apply(ClientboundSetEntityDataPacket packet, ServerSession session) {
                    // modify packet
                    return packet;
                }
            })
            .build())
        .build();
}
```

### How a Plugin Interacts

- Extend `Module`, implement `enabledSetting()` (read from config), optionally override `registerEvents()`, `onEnable()`, `onDisable()`.
- Use the inherited `info()` / `debug()` / `warn()` / `error()` logging methods from `ModuleUtils`.
- Use the inherited `sendClientPacket*()` methods to send packets to the destination server.
- Register via `pluginAPI.registerModule(new MyModule())` in `onLoad()`.

## 5. Pathfinder API

### Purpose

ZenithProxy integrates its own custom pathfinder (not Baritone the mod, but a built-in implementation) for bot navigation. It supports pathing to coordinates, blocks, entities, mining, block placement, and area clearing.

### Important Classes

| Class | Package | Role |
|---|---|---|
| `Pathfinder` | `com.zenith.feature.pathfinder` | Interface declaring all pathfinding operations. |
| `Baritone` | `com.zenith.feature.pathfinder` | Concrete implementation. Implements `Pathfinder`. |
| `Goal` | `com.zenith.feature.pathfinder.goals` | Interface for a pathfinding goal (with `isInGoal()` and `heuristic()`). |
| `GoalXZ` | `com.zenith.feature.pathfinder.goals` | Goal at a specific X,Z coordinate (ignoring Y). |
| `GoalBlock` | `com.zenith.feature.pathfinder.goals` | Goal at a specific X,Y,Z block. |
| `PathingRequestFuture` | (via `com.google.common.util.concurrent`) | ListenableFuture returned by all pathing requests. Use `addExecutedListener()` for completion callbacks. |

### Pathfinder API (from the `Pathfinder` interface)

```java
PathingRequestFuture pathTo(Goal goal);
PathingRequestFuture pathTo(int x, int z);
PathingRequestFuture pathTo(int x, int y, int z);
PathingRequestFuture thisWay(int dist);           // walk in the direction the player is facing
PathingRequestFuture getTo(Block block);          // path to a specific block type
PathingRequestFuture getTo(Block block, boolean rightClickContainerOnArrival);
PathingRequestFuture mine(Block... blocks);       // mine blocks
PathingRequestFuture follow(EntityLiving entity); // follow an entity
PathingRequestFuture follow(Predicate<EntityLiving>);
PathingRequestFuture pickup(ItemData... items);   // pick up specific items
PathingRequestFuture pickup();                    // pick up any items
PathingRequestFuture leftClickBlock(int x, int y, int z);
PathingRequestFuture rightClickBlock(int x, int y, int z);
PathingRequestFuture breakBlock(int x, int y, int z, boolean autoTool);
PathingRequestFuture placeBlock(int x, int y, int z, ItemData placeItem);  // @Experimental
PathingRequestFuture leftClickEntity(EntityLiving);
PathingRequestFuture rightClickEntity(EntityLiving);
PathingRequestFuture clearArea(BlockPos pos1, BlockPos pos2);
void stop();
boolean isActive();
boolean isGoalActive(Goal goal);  // check if a specific goal is being actively pursued
Goal currentGoal();               // returns null if no active goal
```

### Example Usage (from ExampleWanderModule)

```java
import static com.zenith.Globals.BARITONE;
import static com.zenith.Globals.CACHE;
import com.zenith.feature.pathfinder.goals.GoalXZ;

// Check if pathfinder is active
if (!BARITONE.isActive() && pathTimer.tick(20L)) {
    int currentX = MathHelper.floorI(CACHE.getPlayerCache().getX());
    int currentZ = MathHelper.floorI(CACHE.getPlayerCache().getZ());

    GoalXZ goal = new GoalXZ(goalX, goalZ);
    BARITONE.pathTo(goal).addExecutedListener(f -> {
        info("Reached goal! [{}, {}]", goal.x(), goal.z());
        pathTimer.skip();
    });
}

// In onDisable():
if (BARITONE.isGoalActive(goal)) {
    BARITONE.stop();
}
```

### How a Plugin Interacts

- Access via `Globals.BARITONE` (static import `BARITONE`).
- All pathing methods return `PathingRequestFuture` (a `ListenableFuture`). Attach listeners with `addExecutedListener()`.
- Call `BARITONE.stop()` to cancel.
- Check `BARITONE.isActive()` before starting a new path.
- `GoalXZ` and `GoalBlock` are the primary goal types. Implement `Goal` for custom heuristic goals.
- The pathfinder respects the bot tick cycle and requires chunks to be loaded (`CACHE.getChunkCache().getCache().size() >= 8`).

## 6. Inventory API

### Purpose

The inventory system allows plugins to submit batches of inventory actions (click, swap, close container, set held item, etc.) that are executed in a prioritized, tick-delayed queue.

### Important Classes

| Class | Role |
|---|---|
| `InventoryManager` | Singleton manager (accessed via `Globals.INVENTORY`). Accepts `InventoryActionRequest`s and executes them. |
| `InventoryActionRequest` | A batch of `InventoryAction` instances with a priority, optional tick delay override, and an owner. |
| `InventoryAction` | Abstract base for individual inventory operations (e.g. `SetHeldItem`, `CloseContainer`, and many more in `com.zenith.feature.inventory.actions`). |
| `RequestFuture` | Returned by `InventoryManager.submit()`. Allows callers to await completion or rejection. |
| `InventoryCache` | Part of `PlayerCache`. Maintains the snapshot of all open containers and their contents. |
| `Container` | Represents an open container (chest, player inventory, etc.) with its ID, type, title, and items. |

### How It Works

1. Build an `InventoryActionRequest` using its builder, specifying priority, owner, action delay ticks, and a list of `InventoryAction`s.
2. Call `INVENTORY.submit(request)` to enqueue it.
3. The `InventoryManager` picks the highest-priority request each bot tick and executes one action per tick (or all immediately if delay is 0).
4. Each action generates a Minecraft packet (e.g. `ServerboundContainerClickPacket`) that is sent via `Proxy.getInstance().getClient().sendAwait(packet)`.
5. The returned `RequestFuture` resolves when all actions in the batch complete.

### Example Usage (conceptual)

```java
// Build and submit an inventory action
var request = InventoryActionRequest.builder()
    .owner(this)
    .priority(5000)
    .actions(
        new SetHeldItem(0),       // switch to slot 0
        new CloseContainer()       // close any open container
    )
    .build();

INVENTORY.submit(request);
```

### How a Plugin Interacts

- Access via `Globals.INVENTORY` (static import `INVENTORY`).
- Use `InventoryActionRequest.builder()` to construct a sequence of inventory actions.
- The priority system ensures higher-priority actions preempt lower ones.
- Read current inventory state from `CACHE.getPlayerCache().getInventoryCache()`.

## 7. Container Interaction API

### Purpose

Container interaction in ZenithProxy is spread across two systems:

1. **Pathfinder-based**: The pathfinder can walk to a container block and optionally right-click it on arrival.
2. **Cache-based**: The `PlayerCache` tracks open containers and their contents, and exposes methods to open/close containers.

### Important Classes

| Class | Role |
|---|---|
| `Pathfinder.getTo(Block, boolean)` | Path to a block type and optionally right-click it (to open a container) on arrival. |
| `PlayerCache.openContainer(id, type, title)` | Records that a container is now open. |
| `PlayerCache.closeContainer(id)` | Records that a container is now closed. |
| `InventoryCache` | Holds all known containers keyed by container ID. |
| `Container` | Record with `containerId`, `type` (`ContainerType`), `title`, and `contents` (list of `ItemStack`). |
| `InventoryActionRequest` | Can send `CloseContainer` actions. |

### How It Works

- The `PlayerCache` automatically tracks when the server opens/closes containers via packet interception.
- The pathfinder's `getTo()` with `rightClickContainerOnArrival=true` will path to the block and then interact with it.
- The `InventoryManager` executes inventory actions within the context of the currently-open container (checked via `CACHE.getPlayerCache().getInventoryCache().getOpenContainerId()`).

### Example Usage

```java
// Path to any chest and open it on arrival
BARITONE.getTo(Blocks.CHEST, true);

// Read current container contents
var openContainerId = CACHE.getPlayerCache().getInventoryCache().getOpenContainerId();
var container = CACHE.getPlayerCache().getInventoryCache().getContainers().get(openContainerId);
List<ItemStack> contents = container.getContents();
```

### How a Plugin Interacts

- Use `BARITONE.getTo(Block, true)` to navigate to and open containers.
- Read container state from `CACHE.getPlayerCache().getInventoryCache()`.
- Submit inventory actions targeting specific container IDs.

## 8. Block Interaction API

### Purpose

ZenithProxy's pathfinder supports block breaking, placement, left-clicking, and right-clicking -- all via the `Pathfinder`/`Baritone` interface.

### API Surface (from `Pathfinder` interface)

```java
PathingRequestFuture leftClickBlock(int x, int y, int z);
PathingRequestFuture rightClickBlock(int x, int y, int z);
PathingRequestFuture breakBlock(int x, int y, int z, boolean autoTool);
PathingRequestFuture placeBlock(int x, int y, int z, ItemData placeItem);  // @Experimental
```

### Important Classes

| Class | Role |
|---|---|
| `InteractWithProcess` | Internal Baritone process that handles click/break/place operations. |
| `BlockPos` | Immutable record `(int x, int y, int z)`. |
| `Block` | Interface representing a block type (obtained from `Blocks` registry). |
| `ItemData` | Represents an item type (used for placement). |

### How It Works

All block interactions go through the `InteractWithProcess` inside Baritone. They are asynchronous and return `PathingRequestFuture`. The pathfinder handles the necessary movement, rotation, and tool selection automatically.

### Example Usage

```java
// Break a block at specific coordinates
BARITONE.breakBlock(100, 64, -50, true);  // true = auto-select best tool

// Right-click a block (e.g. open door, press button)
BARITONE.rightClickBlock(100, 64, -50);

// Left-click a block (start breaking without pathing)
BARITONE.leftClickBlock(100, 64, -50);

// Place a block (experimental API)
BARITONE.placeBlock(100, 65, -50, Items.DIRT);
```

### How a Plugin Interacts

- All block interactions go through `Globals.BARITONE`.
- Coordinates are absolute world coordinates.
- `breakBlock` with `autoTool=true` will automatically select the fastest tool from the inventory.
- `placeBlock` is marked `@Experimental` and may change.

## 9. Rotation / Look API

### Purpose

ZenithProxy uses a priority-based **input request** system for controlling the bot's movement and camera rotation. Multiple systems (pathfinder, modules, player input) can request control, and the highest-priority request wins each tick.

### Important Classes

| Class | Role |
|---|---|
| `InputManager` | Singleton (accessed via `Globals.INPUTS`). Accepts `InputRequest`s and executes the highest-priority one each tick. |
| `InputRequest` | Immutable request specifying `input` (movement keys), `yaw`, `pitch`, `priority`, and `owner`. |
| `InputRequestFuture` | Returned by `submit()`, allows awaiting completion/rejection. |
| `Input` | Data object for keyboard input state (forward, back, left, right, jump, sneak, sprint, etc.). |
| `InputRequest.Builder` | Builder pattern: `.owner(this).yaw(90f).pitch(0f).priority(7000).build()`. |
| `LookBehavior` | Internal to Baritone. Handles smooth rotation over time. |
| `MathHelper` | Utility for `floorI()`, `calculateRayEndPos()`, etc. |

### Priority Tiers (documented in source)

| Priority | Component |
|---|---|
| 7000 | Baritone pathfinder (default) |
| -5000 | InventoryManager |
| -10000 | InputManager (final processing) |
| -40000 | Baritone post-tick |

Higher numeric values take precedence.

### How It Works

1. A component builds an `InputRequest` using the builder.
2. `INPUTS.submit(request)` is called. If the request has higher priority than the current active request, it preempts.
3. At the end of each tick, `InputManager` passes the winning request to `BOT.requestMovement()` which sends the actual movement/look packet to the server.
4. The Baritone `LookBehavior` computes smooth interpolated rotation towards the current pathfinding goal.

### Example Usage

```java
import static com.zenith.Globals.INPUTS;

// Look at a specific direction
InputRequest lookRequest = InputRequest.builder()
    .owner(this)
    .yaw(90f)
    .pitch(0f)
    .priority(8000)  // higher than Baritone's default 7000
    .build();

INPUTS.submit(lookRequest);
```

### How a Plugin Interacts

- Use `INPUTS.submit(InputRequest.builder()...)` to control rotation and movement.
- Set priority higher than 7000 to override the pathfinder, or lower to let the pathfinder dominate.
- The `InputRequest` can carry only yaw/pitch (for look-only), `Input` (for movement-only), or both.
- `InputRequest.noInput(owner, priority)` creates a request that clears all input.

## 10. World Access API

### Purpose

All world state is mirrored in `DataCache` (`Globals.CACHE`). Every packet from the server updates the cache, making it a real-time snapshot of the bot's known world.

### Important Classes

| Class | Sub-cache | Contents |
|---|---|---|
| `DataCache` | -- | Top-level cache aggregator. |
| `PlayerCache` | `CACHE.getPlayerCache()` | Bot position (`getX/Y/Z`), yaw, pitch, health, food, game mode, inventory, open containers, held slot, teleport queue. |
| `ChunkCache` | `CACHE.getChunkCache()` | All loaded chunks. Access via `getCache()` for block data. |
| `EntityCache` | `CACHE.getEntityCache()` | All known entities. `getEntities().values()` returns a collection of `Entity`. |
| `TabListCache` | `CACHE.getTabListCache()` | Player list entries. |
| `ChatCache` | `CACHE.getChatCache()` | Chat message history. |
| `BossBarCache` | `CACHE.getBossBarCache()` | Active boss bars. |
| `MapDataCache` | `CACHE.getMapDataCache()` | Map item data. |
| `EntityDataManager` | `Globals.ENTITY_DATA` | Entity type registry. |
| `BlockDataManager` | `Globals.BLOCK_DATA` | Block type registry. |
| `RegistryCache` | `CACHE.getRegistriesCache()` | Minecraft registries (items, blocks, etc.). |

### PlayerCache Key Fields

```java
// Position
double getX(), getY(), getZ();
double getEyeY();  // eye height
float getYaw(), getPitch();
double getVelX(), getVelY(), getVelZ();

// Lifecycle
boolean isAlive();          // health > 0
int getEntityId();
float getHealth();

// Inventory
InventoryCache getInventoryCache();
List<ItemStack> getPlayerInventory();
ItemStack getEquipment(EquipmentSlot slot);
ItemStack getEquipment(Hand hand);
int getHeldItemSlot();

// Container
void openContainer(int id, ContainerType type, Component title);
void closeContainer(int id);

// Game state
GameMode getGameMode();
boolean isCanFly(), isFlying();
float getFlySpeed(), getWalkSpeed();
boolean isSneaking(), isSprinting();
```

### EntityCache Key Methods

```java
Map<Integer, Entity> getEntities();  // all entities by entity ID
Entity get(int entityId);
```

### Example Usage

```java
import static com.zenith.Globals.CACHE;

// Get bot position
double x = CACHE.getPlayerCache().getX();
double y = CACHE.getPlayerCache().getY();
double z = CACHE.getPlayerCache().getZ();
float yaw = CACHE.getPlayerCache().getYaw();
boolean alive = CACHE.getPlayerCache().isAlive();

// Iterate all entities
for (Entity entity : CACHE.getEntityCache().getEntities().values()) {
    if (entity instanceof EntityPlayer player) {
        String name = player.getName();
    }
}

// Check if bot is near a coordinate
double dist = CACHE.getPlayerCache().getThePlayer()
    .distanceTo(100, 64, 100);
```

### How a Plugin Interacts

- The cache is read-only for plugins. Updates happen automatically through packet interception.
- Use `CACHE.getPlayerCache()` for bot state, `CACHE.getEntityCache()` for entities, `CACHE.getChunkCache()` for the world.
- `CACHE.getPlayerCache().getX/Y/Z()` gives the **server-authoritative** position (not client-side prediction).
- `CACHE.getPlayerCache().isAlive()` is the correct way to check if the bot can act.

## 11. Event System

### Purpose

ZenithProxy uses an event bus for decoupled communication between components. Modules subscribe to events using the `EventConsumer` pattern.

### Important Classes

| Class | Role |
|---|---|
| `SimpleEventBus` | The event bus (accessed via `Globals.EVENT_BUS`). Fairly standard pub/sub, with synchronous and asynchronous posting. |
| `EventConsumer<T>` | A pairing of event type, optional priority, and handler consumer. Created via the `of()` factory method. |
| `of()` | Static factory from `EventConsumer`: `of(EventType.class, handler)`, `of(EventType.class, priority, handler)`. |

### Known Event Types

| Package | Key Events |
|---|---|
| `com.zenith.event.client` | `ClientBotTick`, `ClientBotTick.Starting`, `ClientBotTick.Stopped` |
| `com.zenith.event.server` | Server lifecycle events (client connected, disconnected) |
| `com.zenith.event.player` | Player join/leave, chat messages |
| `com.zenith.event.chat` | Chat-related events |
| `com.zenith.event.queue` | Queue position updates |
| `com.zenith.event.module` | Module enable/disable events |
| `com.zenith.event.plugin` | `PluginLoadedEvent`, `PluginLoadFailureEvent` |
| `com.zenith.event.message` | In-game message events |
| `com.zenith.event.update` | Update/version events |
| `com.zenith.event.db` | Database events |

### How It Works

**Subscribing** (in a Module):

```java
@Override
public List<EventConsumer<?>> registerEvents() {
    return List.of(
        of(ClientBotTick.class, this::handleBotTick),
        of(ClientBotTick.Starting.class, this::handleBotTickStarting)
    );
}
```

The `Module` base class automatically calls `EVENT_BUS.subscribe(this, ...)` with the returned list on enable, and `EVENT_BUS.unsubscribe(this)` on disable.

**Posting**: Components call `EVENT_BUS.post(event)` for synchronous dispatch or `EVENT_BUS.postAsync(event)` for asynchronous.

**Priority**: Events can have priority ordering:

```java
of(ClientBotTick.class, -40000, this::handlePostTick)  // runs after default-priority handlers
```

Higher numeric priority = runs earlier.

### `ClientBotTick` event

The most important event for plugins. It fires every tick when **no human player is controlling the bot** (i.e., the bot AI is in control).

```java
public record ClientBotTick() {
    public static final ClientBotTick INSTANCE = new ClientBotTick();

    public record Starting() {   // Fires when bot control begins
        public static final Starting INSTANCE = new Starting();
    }

    public record Stopped() {    // Fires when bot control stops (player takes over)
        public static final Stopped INSTANCE = new Stopped();
    }
}
```

### How a Plugin Interacts

- Inside a `Module`, override `registerEvents()` and return a list of `EventConsumer<?>` instances.
- Use `of(EventType.class, this::handlerMethod)` for the common case.
- Use `of(EventType.class, priority, this::handlerMethod)` when ordering matters.
- Events are automatically subscribed/unsubscribed based on module enable/disable state.
- For non-module classes, call `EVENT_BUS.subscribe(instance, consumers...)` and `EVENT_BUS.unsubscribe(instance)` manually.

## Summary of Plugin Registration Flow

```
PluginManager.initialize()
  │
  ├─ Scan plugins/*.jar
  ├─ Read zenithproxy.plugin.json from each JAR
  ├─ Validate mcVersions compatibility
  ├─ Open URLClassLoader
  ├─ Load entrypoint class
  ├─ Instantiate (no-arg constructor)
  │
  └─ plugin.onLoad(PluginAPI)
       │
       ├─ pluginAPI.registerConfig(fileName, ConfigClass.class)
       │     └─ Returns deserialized config POJO, saved at plugins/config/<fileName>.json
       │
       ├─ pluginAPI.registerModule(new MyModule())
       │     └─ ModuleManager registers, calls syncEnabledFromConfig()
       │           └─ If enabledSetting() → enable()
       │                 ├─ EVENT_BUS.subscribe(this, registerEvents())
       │                 └─ PacketCodecRegistries.register(register*PacketHandlerCodec())
       │
       ├─ pluginAPI.registerCommand(new MyCommand())
       │     └─ CommandManager registers Brigadier command tree
       │
       └─ pluginAPI.getLogger()
             └─ Returns ComponentLogger for plugin's own logging channel
```
